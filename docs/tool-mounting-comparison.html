飞书分身 Worker 的工具挂载方式

该对比用于「Worker 需要专属工具」的场景。当前实现已经不使用 Worker 专属工具：feishu_avatar_reply / feishu_avatar_skip 已删除，Worker 直接用全局的 feishu_avatar_send。

四种可行做法，按「实现成本 → 隔离精度」排列，留档备查。

四种做法各自的工具落点

A · 全局注册最省事

注册进 Host 的 tools 注册表，所有 Agent 都能看到。

Host registryreply / skip
你的主会话看得见 ✗ 不该有
Worker 会话看得见
任意子 Agent看得见 ✗
  • 零时序问题，代码最短
  • 工具会污染所有会话的提示词

B · 全局注册 + 条件上一版

register(def, { when })，每个模型步骤按 agent 求值。

Host registryreply / skip + when 条件
你的主会话when=false → 不可见
Worker 会话when=true → 可见
任意子 Agentwhen=false → 不可见
  • DSH 官方支持的条件工具
  • 可见性依赖插件状态文件，状态坏了 Worker 就瞎

C · Agent 作用域当前

拿到 Worker 自己的 agent.ctx，把工具注册进它的作用域。

Host registry只有通用工具
你的主会话看不到
Worker 会话 scopereply / skip 归它所有
任意子 Agent看不到
  • Agent 销毁，注册自动回收
  • 需要等 Agent 就绪，多一层时序

D · 预设作用域最正统

单独做一个 Worker 预设，工具由预设里的插件注册。

Host registry只有通用工具
你的主会话看不到
worker 预设 → 所有 Workerreply / skip
其他预设看不到
  • 声明式，配置里就能看懂
  • 要拆模块 + 预设包，成本最高

对比

维度 A 全局 B 全局 + when C Agent 作用域 D 预设作用域
隔离精度 无 按 Agent 按 Agent 实例 按预设分组
其他会话提示词开销 有（schema 常驻） 无 无 无
依赖插件运行态 否 是（状态文件） 是（会话 id 判定） 否
时序要求 无 无 等 Agent 就绪 无
回收方式 插件卸载时 条件翻转 / 插件卸载 Agent 销毁自动回收 预设卸载
插件卸载安全 简单 简单 需逐个 try/catch 简单
实现规模 约 10 行 约 20 行 约 80 行 新模块 + 预设包
出事时排查难度 低 中（要看状态） 中（要看时序） 低

结论

当前结论：不需要 Worker 专属工具，A（全局注册）就够。Worker 复用 feishu_avatar_send，插件在派发后不再跟踪批次。

如果以后确实要给 Worker 独立能力（例如专用审批工具），再按成本从低到高选 B / C / D；多工具时优先 D 预设作用域。

C 仍有三个真实风险，已做兜底：

  • Agent 就绪慢 → ensure 最多等 3 秒，超时就照常投递，Agent 创建事件到了再补挂；
  • 插件卸载时作用域注册还在 → 逐个 try/catch 释放，失败只记日志；
  • Worker 会话被归档 → 派发前检查，命中就重建会话。
