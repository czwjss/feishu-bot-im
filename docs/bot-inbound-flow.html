机器人侧消息入站流程

飞书长连接推送 → 守卫 → 寻址 → 卡片收尾 → 内容组装 → 提交会话。流式卡片不阻塞其他消息。

主流程

1
事件到达
飞书 im.message.receive_v1 → bridge.handleMessage(data)
2
守卫
任一命中就退出
插件已销毁 / 缺 message_id、chat_id
发送者是机器人且配置禁止 respondToBotMessages
发送者是自己 botOpenId
message_id 已处理过 hasSeen，重放的卡片会跳过这一步
3
权限与寻址
白名单 → 计算 chatKey（群 / 话题）→ 缓存参与者姓名
是否 addressed
话题内：必须 @机器人；话题外：@机器人 或 引用机器人消息
未 addressed → 记入旁听上下文，结束
4
卡片收尾检查
仅 message_type = interactive：先 getMessage 拿渲染内容
streaming_mode = true
挂起：记入 pendingCards，直接 return（不建会话、不调模型）
streaming_mode = false / 无该字段
用最新内容继续往下走
5
文本与指令
展平 text / post / interactive，去掉 @_user_1 占位符
话题内再发 /topic 回提示卡，结束
命中指令 /menu、/topic 等先执行，命中即结束
6
类型白名单
text / post / image / file / interactive
其他类型（语音、视频） 回「暂不支持」，结束
7
引用与附件
解析 parent_id 取被引用消息 → 图片/文件/富文本走 #inbound.build 下载
8
组装与提交
只有裸 @，没有正文 群里已有会话 → 最小 prompt；没有会话 → 提示卡片
正常内容 打 processing 表情 → #submitPrompt → 绑定/创建 Session → 跑一轮

流式卡片的分支

1. 挂起streaming_mode=true
pendingCards.set(id)
2. 复查每 30 秒一次
getMessage(id)
3. 判定看 streaming_mode
和 update_time
4. 出队收尾重放 / 超时丢弃
↓
收尾streaming_mode=false → 用最新内容 handleMessage(data, {resubmitted:true}) 重放，跳过 hasSeen
丢弃创建超 10 分钟（平台自动关闭流式模式）→ 移出列表，不入会话、不标记

关键事实

卡片更新不会推送事件
一条卡片只推一次 receive；内容是初始态，所以必须主动 getMessage 查状态。
收尾判定靠 streaming_mode
卡片 JSON 2.0 的 config 字段；飞书 10 分钟后会自动关闭流式模式。
只有 10 分钟上限
平台会在 10 分钟后自动关闭流式模式，超过就丢弃，不再看更新时间。
挂起不阻塞
挂起只影响这一条卡片，同聊天的其他消息照常入站。

已知边界：挂起列表在内存里，插件重载后丢失；卡片收尾重放可能晚于期间到达的新消息。
