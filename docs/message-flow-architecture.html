飞书消息接入与回复架构

两条独立链路：机器人身份走事件推送，用户分身走轮询。它们在 DSH 里汇合到同一套 Agent 与会话上。

机器人身份（tenant_access_token / 事件推送） 用户分身（user_access_token / 轮询） DSH Host / Agent

链路一　机器人身份：事件推送 实时

1
飞书长连接事件
im.message.receive_v1 群/私聊消息 · card.action.trigger 卡片按钮
入口 src/feishu.js → startLongConnection
▼
2
消息桥接与准入
src/bridge.js → handleMessage
去重（state.hasSeen）→ 白名单/权限 → 是否被 @ 或引用机器人 → 未命中的进旁听缓冲
▼
3
引用与上下文组装
拉父消息（含引用图片、卡片内嵌图片）→ 命中 /命令 直接执行 → 否则组装注入块： 引导语、来源、引用、旁听、同步
▼
4
投递到 DSH 会话
src/harness.js → session.prompt；一个飞书会话 → 一个 DSH Session
▼
5
流式回写
agent/assistant-stream → CardKit 卡片逐段更新（失败降级为普通卡片）→ 结束补最终态
▼
6
人工环节回传
审批 / 选择题 → 飞书卡片按钮 → card.action.trigger → bridge.onCardAction → 回到会话继续

链路二　用户分身：轮询收件箱 默认每 60 秒

1
定时轮询
src/user-identity/monitor.js → pollOnce
窗口：min(游标−1s, 现在−2min)，每会话串行，单轮最多 100 条
▼
2
过滤与触发判断
跳过：自己发的、系统消息、已删除 · 触发规则：私聊全收 / 群聊仅 @我·回复我 / 关键词
被过滤的消息也会推进游标，不会每轮重判
▼
3
去重与噪点清理
同一 message_id 原地刷新 → 更新旧记录，不新增未读 · 「已收到/正在处理」超过 2 分钟自动丢弃 · 卡片正文拉平成可读文本，<at> 渲染成姓名
▼
4
本地收件箱
~/.dsh/integrations/im-feishu/monitor-state.json（0600，每会话 50 条）
不调用模型，不自动回复
▼
5
未读提示注入
im-feishu-user:inbox 系统提示段：只给数量与会话名，例如「飞书分身收件箱有 2 条未读：小金刚 2 条」
▼
6
Agent 读收件箱
工具 feishu_avatar_inbox：默认只取未读并标记已读，可按会话过滤
▼
7
起草
工具 feishu_avatar_draft：只落库成待确认草稿（30 分钟过期），不发送
▼
8
人工确认
设置 → 飞书机器人 → 分身 → 消息监听 → 待确认草稿：发送 / 忽略（RPC）
▼
9
以本人身份发出
有原消息则走 im/v1/messages/:id/reply 保持引用，否则发到会话； token 过期自动刷新一次
用户明确说「直接发」时才跳过草稿，直接用 feishu_avatar_send
为什么是轮询：飞书的事件推送只发给应用（机器人）， 个人身份拿不到「别人给我发的消息」的实时事件，所以分身只能按游标拉取。代价是延迟受轮询间隔约束。

汇合点与出口

A
同一套 DSH 能力
两条链路最终都落到 DSH Agent：工具、技能、子代理、审批、会话持久化完全共用。
B
两种身份不能混用
feishu_bot_* 群里显示「小金刚」
feishu_avatar_* 群里显示「陈志文」
C
出口清单
feishu_bot_send 机器人发卡片/文件
feishu_avatar_send 本人发卡片/图片/文件
流式卡片由 bridge 自动更新，不占工具
D
设置页通道
client/identity.js → POST /api/im-feishu → src/rpc.js：机器人管理、分身授权、监听与草稿
